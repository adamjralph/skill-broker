# Skill identity hash depth

**Status:** research finding for wayfinder ticket #3  
**Date:** 2026-09-19  
**Question:** Is `SKILL.md` sufficient for content identity, or must the package's supporting files also be included?

## Finding

`SKILL.md` alone is sufficient for deduplicating the observed package copies **only in the
usual case**, but it is not a safe content identity. In the duplicate-exposure set from the
catalogue reconnaissance, **2 of 364 duplicated content groups differ in supporting files**
(**0.55%**). Thus a SKILL-only hash would collapse two real package variants (and miss the
change in their executable/reference payload).

The practical recommendation is to keep two hashes:

- a cheap `skill_md_sha256` for retrieval/deduplication of the prompt-facing document; and
- a canonical package hash over the normalized package file set, including `references/`,
  `scripts/`, `templates/`, and `assets/`, for identity, storage, provenance, and change
  detection.

## Method

The reconnaissance defines the duplicate population as the 364 `SKILL.md` contents found at
more than one path (catalogue-topology.md, lines 20–26 and 38–46). I regrouped those exposures
by the recorded SHA-256 of `SKILL.md`, then compared the relative path and SHA-256 of every
file below the four supporting directories. As with the reconnaissance, VCS/dependency/cache
directories were excluded (catalogue-topology.md, lines 20–25 and 69–72). Generated
`__pycache__/*.pyc` files were also excluded: they are runtime artefacts and otherwise create
false package differences despite identical source files.

The comparison is over package contents, not realpaths. Therefore symlink exposures of one
physical directory count as identical underneath, while independent copies are compared byte
for byte. This matches the catalogue's distinction between “same file, many exposures” and
content/name divergence (catalogue-topology.md, lines 107–119).

## Results

| Same `SKILL.md` content group | Supporting files identical | Supporting files differ | Differing rate |
| ---: | ---: | ---: | ---: |
| 364 | 362 | 2 | **0.55%** |

The result is a **group rate**: a group is “different” if any two package copies in that
same-SKILL group have different supporting-file paths or bytes. It is not a claim that only
0.55% of all skills have support files; it measures the specific collision risk in the
reconnaissance's duplicate population.

### Concrete identical-underneath case

`hermes-agent` has the same `SKILL.md` SHA-256
`a111466ce81ccdad8bccc7f670c7946df9d9f8b639399f28bd2958f5bce92c56` at:

- `~/research/hermes-pr-opportunities/skills/autonomous-ai-agents/hermes-agent/`
- `~/research/hermes-pr-evidence/full-suite/baseline/skills/autonomous-ai-agents/hermes-agent/`

The supporting trees match: the 18 `references/*.md` files and three templates
(`templates/clock.mjs`, `templates/plugin.js`, `templates/skin.yaml`) have the same relative
paths and bytes in both packages. For example, `references/cli-reference.md` hashes to
`339563a94249…` and `templates/plugin.js` to `a63c8f879756…` in each. These are genuine
redundant copies, so a package hash adds no distinction here.

### Concrete differing-underneath case

`git-guardrails-claude-code` has the same `SKILL.md` SHA-256
`69b291d655626a01602b998a1836fcb93c058ede68dfafddfd71e87f17074764` at:

- `~/Documents/skills-archive/skills/skills/misc/git-guardrails-claude-code/`
- `~/backups/life-os/life-os-07-09-2026/mattpocock/skills/git-guardrails-claude-code/`

Both contain `scripts/block-dangerous-git.sh`, but the file hashes differ:
`234922b83c0a…` versus `eafbc9ad20f5…` (507 bytes versus 1,082 bytes). A SKILL-only identity
would incorrectly say these executable packages are identical.

A second differing group is `hermes-agent`: its shared `SKILL.md` is unchanged, while
`references/desktop-plugins.md` and `references/windows-quirks.md` differ between the
Hermes optional/runtime/profile copies. This confirms the phenomenon is not limited to
scripts.

## Decision implication

Do not make the package identity equal to the `SKILL.md` hash. Use a deterministic manifest
of normalized relative paths plus file bytes (or per-file SHA-256s), then hash that manifest.
Exclude generated bytecode and other explicitly excluded cache/VCS material, document the
normalization, and retain the `SKILL.md` hash as a separate index field. The low observed rate
supports deduplication optimizations, but not SKILL-only identity: the rare collisions are
exactly the cases where executable or reference content can change behavior.
