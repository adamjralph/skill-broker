## Store implications

1. Canonicalize the two Git checkouts as separately owned sources: `coreyhaines31/marketingskills` and `mattpocock/skills`. A broker/store can pull those directly, but should detect the local marketingskills working-tree change before update.
2. Record Cursor `pstack` as a publisher/plugin source, not as a Git checkout. Refresh through the plugin installer rather than attempting `git pull` in the archive.
3. Treat BB runtime directories as derived artifacts. Their hashes identify a content/cache snapshot, not an upstream repository. A catalog entry should retain the BB source/install identity if available elsewhere, but must not infer Git ownership from `skill-tree:<hash>`.
4. Treat `~/.agents/skills` and `~/Work/.agents/skills` as **no-upstream** until a manifest, installer record, or repository is found. The presence of `find-skills` instructions does not establish that every installed skill came from the Skills registry.
5. Treat `~/.hermes/skills` as mixed: Hermes bundled content has a clear upstream, while optional/user content and profile links must retain their individual source paths. Profiles should be represented as references/overlays, not copied canonical homes.

## Evidence limitations

The Git comparisons in the archive investigation compare local branches with locally stored `origin/main` refs; they do not prove that the remote was contacted during this audit. The pstack author mismatch (“poteto” versus “Lauren Tan”) remains unresolved. Filesystem absence of `.git`, package/version metadata, and provenance statements establishes “no discoverable upstream locally,” not proof that no upstream exists anywhere.
